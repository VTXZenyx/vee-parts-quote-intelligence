# Technology and product research

## Initial reuse decisions · 18 November 2026

Keep engineering approval, customer pricing and quote arithmetic under VEE's control. A smoke test of an industrial RFQ parser showed how a plausible text match can erase a material or dimensional distinction. Search can propose a candidate. Recording the customer's requirement, the catalogue value, its source and the employee's decision allows a reviewer to see whether it is suitable.

All nine GitHub repositories below were publicly readable. We inspected committed source, dependency manifests, licences and up to 15 recent commits from each default branch. Dates are Git author dates. The links pin the revision inspected. Source inspection establishes implementation paths only. Runtime evidence is identified separately. No external code, data or model weights were incorporated into VEE, no repository installers ran, and no accounts or credentials were connected.

## Runtime checks

Two upstream modules were read in full and exercised in temporary directories using Python's standard library, isolated mode, disabled site imports and a cleared process environment. The other repositories received static review only. No supplier transaction, LLM request, email, workflow deployment or production database operation was attempted.

| Reviewed module | Input | Observed result |
| --- | --- | --- |
| RFQ Copilot `catalog.py` | `parse_quantity("qty 2")` | Returned `2.0`. |
| Same module | `parse_size("M12x50")` and `parse_size("M12x80")` | Both returned `M12`. Length must be retained as a separate requirement. |
| Same module | `parse_material("bronze")` and `parse_material("stainless steel")` | Returned `Brass` and `SS304` respectively. These substitutions would create unsupported material specifications. |
| IRISP `unpack_spare_parts.py` | Generated two ZIPs containing 19 expected inner ZIPs and one synthetic object folder per inner ZIP. Ran `plan_bundles` and `unpack` and checked all output bytes. | All 19 fixture files appeared in the expected split structure. The actual image archive contents, labels and retrieval quality remain unverified. |

## Commercial product research

Requests to every vendor's supplied public HTTPS site failed at the environment's outbound proxy with `CONNECT 403`, including a retry with expanded network permission. The vendor servers did not return any page content. Product capabilities, private architecture, integrations and accuracy therefore remain unverified in this investigation. No commercial claims informed a technology or purchasing decision.

| Vendor | Public page requested | Evidence to collect on a subsequent pass |
| --- | --- | --- |
| Distro | [Vendor site](https://distro.app) | Supported RFQ inputs, evidence presented during item review, and documented ERP integration boundaries. |

Close the commercial review with dated vendor documentation, a direct source for each capability and a distinction between published descriptions and behaviour actually tested. For a future retrieval experiment, record exact-identifier accuracy, top-k candidate recall, false verified matches on deliberately confusable parts, abstentions, latency and cost using the same approved test set. Production candidates additionally need a pinned dependency and data-rights review against the particular version, model weights and archive used.

## Optional V3 extraction SDK

Reviewed the published openai-python 3.57.0 wheel metadata, client source, completion API and dependency lock before installation. The official Python SDK uses Apache-2.0 and lists httpx2, anyio, jiter, Pydantic, sniffio and typing-extensions as direct dependencies. The base Flask installation remains independent. The optional adapter uses structured Chat Completions and a fixed HTTPS endpoint with storage disabled. Provider processing and retention terms still apply to submitted text. This milestone authorises synthetic records only. No service request was needed to exercise the SDK through an in-memory HTTP transport.

[SDK repository](https://github.com/openai/openai-python) · [Release metadata](https://pypi.org/project/openai/3.57.0/) · [API data controls](https://platform.openai.com/docs/guides/your-data)

The offline message fixtures use the documented Gmail Message and MessagePart fields and Graph message, internet header and file-attachment shapes. Only the supported text subset is exercised.
